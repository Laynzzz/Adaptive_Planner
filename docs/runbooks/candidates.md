# Invalid candidate or infeasible request

A validator rejection is an engineering incident; a proved infeasible schedule is a product outcome. Inspect job reason, candidate status and constraint report. The aggregate validator-rejected gauge and job-result trace identify the former. Do not activate UNKNOWN or a candidate with hard violations, and never repair it by deleting protected commitments.

Keep the current active plan. Reproduce using a new synthetic fixture with the same constraint shape and fixed clock; do not export a user's task/calendar text. Verify independently with `validate_candidate`. Roll back the routing release to fixed CP-SAT if a learned policy is implicated; model inference never bypasses the validator. An infeasible input should show its meaningful typed constraints and support a reviewed what-if change.

After the fix, run the precise regression plus affected solver/worker tests. Confirm rejected candidates remain unselected and the existing active pointer is preserved. Link fixture, code revision and solver metadata in the incident record.
